# File an actionable issue

Use this skill when issue preparation or filing is requested. A bug report or
feature discussion alone does not authorize creating tracker work.

Follow the [change and test policy](../../../docs/change-policy.md) for scope and
acceptance coverage, and [GitHub access](../../../docs/orchestration/environment.md#github-access)
for transport, credentials, and write verification. Missing write credentials
block filing, not investigation or a complete draft.

## Investigate

Capture the reported behavior, location, and desired result. Inspect the current
code and relevant domain contract before asking questions.

- For a bug, distinguish the reproduced symptom from the suspected mechanism.
  Cite the actual owner; label an unproven cause as unproven.
- For a feature, search existing code and neighboring surfaces before claiming
  the capability is absent. Name what exists and the specific remaining gap.
- Keep verified facts separate from assumptions. Resolve assumptions through
  code, existing rulings, or the user before presenting them as requirements.

## Check the tracker

Check open and closed issues with several relevant terms. Use paginated REST
listing and local filtering when search is unavailable. Issue-list responses also
include PRs; distinguish them when assessing duplicates.

Read each near match's complete body and all comments. If the investigation is
long, recheck before filing so a new ruling is not missed.

- Duplicate: show the existing issue and stop creating a new one. A comment or
  amendment needs authorization for that write.
- Adjacent: cross-reference the issue and explain the different scope.
- Dependency: use a standalone `Depends-on: #123` line.
- Umbrella: name `Part of #N` and the specific checklist item.

## Resolve decisions

Batch only questions that current code and session instructions cannot settle.
Use [decision classes](../../../docs/orchestration/decision-classes.md) to check
ambiguity, placement, numbers, wrong-result cost, conflicting rulings, coupled
work, and exceptions to universal rules. These are prompts for investigation,
not seven mandatory questions.

Explain options in terms of what a person sees or can do, with a recommendation
and the impact of each choice. Use existing constants or measurements for limits.
Do not reopen a settled decision at confirmation.

If a consequential decision remains unresolved, keep it explicit in the draft.
An authorized issue intended for a later owner decision carries `needs-human` and
one concrete question. Without authorization to file that unresolved draft, save
it for review and report it as unfiled. Noninteractive work does not supply consent.

## Draft

Use a one-clause title of at most 72 characters. Name the defect or requested
outcome; put supporting detail in the body. Keep the brief proportional to the
change rather than filling a template with redundant sections.

A feature normally needs **Problem** and **Proposal**; a bug needs **What is
wrong**, **Consequence**, and **Fix**. Add invariants or exclusions only when they
help distinguish a correct implementation. Include:

- Acceptance criteria describing observable behavior and meaningful verification.
  Prefer existing coverage; do not require new tests by default.
- Repository-rooted paths and symbols for evidence. When citing a line, name the
  code on that line so a later reader can verify it after edits.
- Related issues/PRs under **Refs**, with a short reason for each reference.
- Final decisions from the discussion and any remaining owner question.

Propose reuse, simplification, or removal before a new abstraction. State what a
conversion replaces; do not prescribe a registry or scanner when types or an
existing owner can enforce the contract. If found during other work, note that
provenance briefly without appending an incident narrative.

## Labels and priority

Follow [queue labels](../../../docs/orchestration/labels.md): at least one domain
and exactly one priority slot, `P0`–`P3` or `parked`. Validate against
`KNOWN_LABELS` in [reconcile-tracker-core](../../../scripts/orchestration/reconcile-tracker-core.ts),
not the live label list. Do not duplicate that taxonomy here or invent a label.

Use the [dispatch priority rules](../../../docs/orchestration/dispatch.md#dispatch).
An active infrastructure bottleneck can warrant P1; a latent isolated flake is
normally P3; ordinary scoped features and cleanup are generally P2–P3.
Agent-discovered work defaults to P3, subject to the documented demonstrated
regression and owner-authorized audit exceptions. Explain priority in the draft;
ask only when the evidence cannot settle it.

## File and verify

Finish the reviewable package first: title, labels, and complete body. Honor any
existing authorization to file; otherwise obtain approval for that package before
creating the issue. Incorporate requested changes before the write.

Prepare a JSON payload file so newlines and literal text survive shell handling:

```bash
gh api --method POST repos/FloorLamp/allos/issues --input /tmp/issue.json
```

Use a task-specific temporary filename. Check the response and verify the created
issue under the shared GitHub write policy, then report its number and URL. If
access is blocked, leave the complete draft and say it was not filed.

If the premise already shipped or an existing ruling resolves it, report the
evidence and file nothing.
